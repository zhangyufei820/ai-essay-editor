# 积分统一与月度重复发放修复

## 已确认根因

生产 `credit_transactions_type_check` 仅允许 purchase、consume、refund、bonus、register、manual。旧月度发放代码先修改余额，再插入不被允许的 `membership_grant` 流水，导致余额已加、流水失败，下一次定时任务再次发放。生产月度任务日志中，最近两次均为订单 152 的第 1—4 期执行失败；每次对应 4 × 12000 = 48000 积分。尾号 3937 当前旧余额 527630，比最后一笔流水余额 431630 多 96000，与这两次发放相符。

另有 3 组双身份分别持有注册赠分及消费记录。旧扣费 RPC 和部分查询入口按传入身份创建 1000 积分，可能重新创建旧账户；读取、扣费和会员发放因此落在不同身份。

## 处理决定

- 保留已经入账的余额，不追扣历史误发或已消耗的重复注册赠分。迁移只转移现有余额，合并前后总额不变，不额外补发积分。
- 对可核实的 96000 历史入账差额补记审计流水，不再次修改余额；更早历史衔接差异保留原始证据，不凭推测补账或扣账。
- 将订单 152 已反复尝试过的第 1—4 期标记为已核对，避免新旧版本再次补发；下一期按实际到期时间处理。
- 只使用持久化的精确 Authing 桥接。测试账号的同邮箱第三身份没有充分身份凭证，本次不合并。

## 代码与数据库变更

- 迁移 014：`ensure_credit_account` 通过精确桥接统一账户，在同一事务中迁移残留积分并初始化一次；月度发放初始化缺失账户时从 0 开始，不额外赠送注册积分。
- 迁移 014：新增 `membership_credit_grants`，用 `(order_id, period)` 唯一键记录已发放和历史已核对期次；`grant_membership_credits_once` 将余额、有效 bonus 流水和去重记录放在一个事务中。
- 迁移 015：原子扣费先解析并统一账户，原有 RPC 签名不变，旧身份的请求也扣统一余额。
- 积分页、聊天、作文批改、通用积分查询和初始化使用统一 RPC；查询失败时不再执行覆盖余额的 upsert 或虚构 1000 积分。
- 积分页将服务不可用显示为可重试错误，避免渲染为 0 分。
- 新函数仅授权 service_role，普通登录用户和匿名用户不可直接执行；支付回调校验、网关和环境文件不变。

## 验证

- 全套 Jest：101 套通过、1 套原有跳过；626 项通过、7 项原有跳过。
- 全仓 ESLint：0 错误、67 条已有警告。
- 完整本机 Webpack 生产构建、TypeScript 和 85 个页面生成通过。测试构建使用本机模拟配置，不作为生产镜像发布。
- 本机 PostgreSQL 真实事务测试：24 个并发请求覆盖双身份只初始化一次和同期只发放一次；验证扣费/发放流水失败会回滚余额，历史期次不会重发，余额不足与未来期次被拒绝，匿名/普通用户无法调用变更 RPC，缺失付费账户不会额外获赠注册积分。
- 匿名 4 组数据实演：余额总额 3023430 不变，4 个旧账户归零，4 个期次已核对；重复执行无改动。人为改变第 4 组余额时，整批回滚，前 3 组也不发生变更。
- 本机 Chrome：打开积分页，显示 4423 和双身份明细；刷新保持余额；模拟不可用响应后显示“积分暂时无法读取”，点击重新加载恢复 4423。未使用真实用户凭据或访问生产账本。

## 发布顺序及恢复边界

1. 在服务器现有环境中构建此提交，仅构建 nextjs，保留现有镜像。
2. 再次核查生产版本、函数定义和 4 组余额；在一个事务内执行迁移 014、015 和一次性核对脚本，然后通知 PostgREST 刷新 schema。
3. 只切换 shenxiang-nextjs，核对健康版本及容器内编译产物。
4. 用项目测试账号走真实生产登录、积分、明细与刷新；核查全部桥接和月度任务的 dry-run、重复执行结果。

应用恢复不能重新启用旧的非原子月度发放路径。新增去重表与审计流水应永久保留，防止恢复后重复发放。已经发生后续消费时，不可直接撤销此次划转；任何账务修正须另做有审计的抵补事务。
